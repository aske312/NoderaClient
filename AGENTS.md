# Работа с ветками

- Все доработки выполнять в `d-win`. Дополнительные ветки без запроса пользователя не создавать.
- `d-win` идёт вперёд; `pro-win` догоняет её после проверок, перемещаясь на уже существующий проверенный коммит из `d-win`.
- Продвигать `pro-win` только через fast-forward (`git merge --ff-only <проверенный-коммит>` и обычный `git push`). Не создавать merge-коммиты, не использовать squash/rebase для продвижения и не сливать `pro-win` обратно в `d-win`.
- Не вносить отдельные коммиты непосредственно в `pro-win`. При расхождении истории остановить продвижение и выяснить причину, не применять force push.
- Pull request допустим для проверки и просмотра изменений; кнопки Merge/Squash/Rebase для переноса между этими ветками не использовать.
- После продвижения оставлять рабочую копию на `d-win`. Равенство веток после выпуска нормально: следующие доработки снова выводят `d-win` вперёд.
- В `d-win` сохранять минимальные проверки CI. Полный прогон выполнять перед продвижением в `pro-win` и при выпуске продукта.

Подробности: `docs/versioning.md`.
