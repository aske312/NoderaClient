# Версии

Источник версии: `nodera/__init__.py`. Формат `MAJOR.MINOR.PATCH`: несовместимость / новые возможности / исправления. Меняется при подготовке релиза; тег — `v<версия>` после проверок. Номер версии, ветка и идентификатор сборки решают разные задачи.

## Постоянные ветки

Сейчас обе ветки предназначены для Windows: `d-win` — разработка, `pro-win` — выпуск продукта. Схема будущих платформ будет определена при появлении их реализации. Версия приложения пока общая; суффикс платформы в номер версии не добавляется.

| Ветка | Назначение | Результат CI |
| --- | --- | --- |
| `d-win` | Текущая разработка и тестирование будущего обновления | Только Ruff и синтаксис Python, затем тестовая portable-сборка; без pytest и проверки форматирования |
| `pro-win` | Проверенный код для выпуска пользователям | Ruff, форматирование, весь pytest и portable-сборка; установщик через release workflow |

Все изменения делаются в `d-win`. Она движется вперёд, а `pro-win` после проверок догоняет её через fast-forward: указатель релизной ветки переносится на уже существующий проверенный коммит. Дополнительные ветки и merge-коммиты для этого не создаются. История линейная, `pro-win` всегда является предком `d-win` или совпадает с ней. Совпадение сразу после выпуска нормально; следующие изменения снова выводят `d-win` вперёд.

Для pull request набор проверок определяется целевой веткой: в `d-win` — минимальный, в `pro-win` — полный. Release workflow также выполняет полный набор проверок перед сборкой установщика.

## Порядок выпуска

1. В `d-win` завершить изменения и указать следующую версию в `nodera/__init__.py`.
2. Подготовить `docs/releases/v<версия>.md`, дождаться успешного CI и проверить тестовую сборку.
3. При необходимости открыть pull request `d-win` → `pro-win` для полного прогона CI, но не использовать кнопки Merge, Squash или Rebase. После успешных проверок продвинуть `pro-win` только через fast-forward:

   ```powershell
   git fetch origin
   git switch pro-win
   git pull --ff-only origin pro-win
   git merge --ff-only <проверенный-коммит-из-d-win>
   git push origin pro-win
   git switch d-win
   ```

   Использовать конкретный проверенный коммит, если `d-win` успела уйти вперёд. Если fast-forward невозможен, остановиться и разобраться в расхождении; не создавать merge-коммит и не применять force push.
4. На коммите из `pro-win` создать и отправить тег, например для следующего исправления:

   ```powershell
   git switch pro-win
   git pull --ff-only origin pro-win
   git tag -a v0.0.3 -m "Nodera 0.0.3"
   git push origin v0.0.3
   ```

5. Release workflow проверит принадлежность коммита ветке `pro-win`, формат тега и совпадение с версией приложения, выполнит проверки и создаст черновик GitHub Release с установщиком и SHA-256.
6. Проверить установщик из черновика и опубликовать релиз. Только опубликованный стабильный релиз становится источником обновления клиентов.
7. Вернуться к разработке:

   ```powershell
   git switch d-win
   git pull --ff-only origin d-win
   ```

Теги выпущенных версий не перемещаются. Для исправления опубликованного выпуска нужен новый PATCH. Исправления, в том числе срочные, сначала вносятся в `d-win`, затем проверенный коммит продвигается в `pro-win`. Отдельные коммиты в `pro-win` и обратное слияние в `d-win` не используются.

Ветка по умолчанию — `d-win`. Защита `pro-win` должна допускать продвижение проверенного коммита через fast-forward и запрещать нелинейную историю, force push и удаление. Обязательное слияние через GitHub PR не используется, поскольку оно создаёт или переписывает коммиты вместо продвижения существующих. Настройки защиты выполняются отдельно в GitHub.

## Идентификатор сборки

`scripts/build_metadata.py` записывает UTC build ID, время и Git-ревизию в `nodera/resources/build-info.json`. Версия попадает в Windows FileVersion/ProductVersion, build ID — в PrivateBuild и подсказку интерфейса. Сборщик не меняет версию и не публикует релизы.

Упаковка: `packaging/Nodera.spec`, запуск — `scripts/build.ps1` (`-Clean` для полной пересборки). Результат: `dist/builds/<build-id>/Nodera`, ярлык — `dist/Nodera.lnk`. Старые сборки сохраняются.
